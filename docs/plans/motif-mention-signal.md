# 플랜 — 프롬프트의 모티프 언급을 감지해 프론트로 시그널 반환

> 상태: **미실행 제안** (2026-08-03). 선행 맥락: `docs/reviews/motif-fixed-colors-followup.md`
> "미해결 2" — stripe 없는 플랜에 지명색이 2개 오면 배치 실패로 재저작 루프 후 422가 된다.
>
> 재해석: 이 상황은 "색을 넣을 자리가 없는 오류"가 아니라 **사용자가 디자인 생성 문장 안에서
> 모티프(생성·변경)를 요청한 경우**로 보는 게 맞다. 모티프 생성은 디자인 생성과 분리된 별도
> 플로우(모티프 피커)이므로, 워커/api가 이를 감지해 프론트로 시그널을 돌려주고 프론트는
> 모티프 피커로 사용자를 유도한다(예: 피커 하이라이트/애니메이션, 안내 문구).

## 동작 개요

1. **감지(worker)** — 디자인 생성·구성 수정 문장에서 모티프를 향한 요청을 분류한다.
   - 후보 신호: 모티프 대상 어휘(`무늬`, `모티프`, `도형`, `꽃`, `로고` 등 명사 언급),
     지명색이 바탕/스트라이프 슬롯에 배치 불가한 잔여로 남는 경우(현 raise 지점),
     LLM 저작 결과가 모티프 레이어 변경을 시사하는 경우.
   - 저작 LLM 호출이 이미 있는 경로이므로 별도 모델 호출 없이 기존 응답에 분류 필드를
     추가하는 방향을 우선 검토(비용 0). 규칙 기반(named_colors의 `_MOTIF_WORDS` 계열)을
     보조로 쓴다.
2. **반환(api)** — 생성/패치 응답에 구조화 시그널을 추가한다. 예:
   `{"motif_intent": {"detected": true, "subject": "동백꽃", "reason": "motif_mention"}}`.
   422로 끝내는 대신 가능한 부분(바탕 색 등)은 반영하고 시그널을 함께 돌려주는 것을
   기본 동작으로 한다 — "일부 반영 + 다음 행동 안내"가 "전체 실패"보다 낫다.
3. **프론트(store)** — 시그널 수신 시 모티프 피커에 어포던스를 준다.
   - 피커 카드 하이라이트/애니메이션(`animation-craft` 하네스 준수), 감지된 subject를
     피커 검색어로 프리필, 스낵바/캡션으로 "모티프는 여기서 만들 수 있어요" 안내.
   - 시그널은 1회성 UI 힌트다 — 세션 상태로 저장하지 않는다.

## 열린 설계 포인트 (실행 전 확정)

- 감지 주체: LLM 저작 응답 필드 vs 규칙 기반 vs 혼합 — 오탐/미탐 허용선 결정.
- 현 named_colors raise 경로와의 관계: 시그널 도입 시 raise를 "부분 반영 + 시그널"로
  대체할지, 재저작 1회는 유지할지.
- api 응답 스키마 위치(생성 응답 vs 별도 diagnostics)와 api-client 재생성 범위.
- subject 프리필의 언어 처리(사용자 원문 그대로 — 모티프 검색이 한국어 직송이므로 무가공).

## 작업 항목 (실행 시 상세화)

- worker: 분류 신호 정의·저작 응답 스키마 확장·`named_colors` 잔여색 경로 연결.
- api: 응답 시그널 필드 추가, `pnpm codegen` 동반.
- store: 피커 어포던스(하이라이트·프리필·안내), 시그널 소비 테스트.
- 문서: worker-pipeline.md 응답 계약, ARCHITECTURE 플로우 갱신.
