# 토큰 단가 재정립 (usage 로그 실측 기반)

**전제**: 2026-08-14에 넣은 `provider_usage` 로깅이 충분히 쌓인 뒤 실행한다. 지금의 단가
25/12/100(1토큰 ≈ 1원 스케일)은 **문자수 환산 추정 원가**로 안전 마진을 잡은 값이다 —
실측으로 검증하지 않았다. 특히 모티프의 장당 8.4원($0.006)은 대표값이고 gpt-image-2는
token-based billing이라, 이 항목이 실측 1순위다.

관련: `docs/api-spec/money.md §6`(단가 정본), `docs/reviews/llm-openai-migration-2026-08-03.md`.

## 왜 필요한가

과거 단가가 틀어진 원인은 "모델 원가가 변했는데 숫자를 안 고쳤다"가 아니라 **원가를 측정하지
않았다**는 것이다. 5/2/0은 첫 생성이 후보 이미지를 여러 장 굽던 구조에서 정해진 뒤, 단일
디자인화(`e910eb5`)·Gemini→OpenAI 전환·Recraft→gpt-image-2 전환·luna 80% 인하를 거치며
근거를 잃었다. 같은 일을 반복하지 않으려면 실측 → 재정립을 한 번 돌려야 한다.

## 실행 조건 (둘 다 충족)

1. **표본**: `operation=author_design` 로그 **200건 이상**, `author_patch`·`generate_motif`
   각 **50건 이상**. 근거: 저작은 재시도 횟수(1~4콜) 분산이 커서 p95를 보려면 100건 이상이
   필요하고, 200건이면 하루 몇십 건 규모에서 1~2주면 모인다. patch·모티프는 콜 수가 고정에
   가까워(1콜, 1~2장) 50건이면 평균이 안정된다.
2. **기간**: 최소 **14일** 연속. 프롬프트 리비전·모델·스키마를 바꾼 날이 있으면 그 이후
   구간만 센다(입력 토큰이 리비전마다 달라진다).

표본이 안 차면 실행하지 말고 기다린다. 추정치를 실측으로 포장하는 게 이 플랜의 실패 모드다.

## 절차

1. **집계** — Cloud Logging에서 `provider_usage`를 operation별로 뽑아 다음을 낸다:
   `count`, `input` 평균·p95, `output` 평균·p95, `reasoning` 평균, `cached` 비율.
   요청 1건당 콜 수(= `author_design` 로그 수 / 생성 요청 수)도 반드시 낸다 — 재시도가
   원가의 최대 변수다.
2. **원가 계산** — 그 시점 공시 단가로 환산한다(단가도 함께 기록: 모델·날짜·USD/1M).
   `cached` 입력은 할인 단가를 따로 적용한다. 환율은 계산일 기준을 명시한다.
3. **추정과 대조** — 아래 표의 추정 원가와 실측을 나란히 적는다. 3배 이상 벌어진 항목이
   있으면 원인을 먼저 규명한다(reasoning 토큰, 재시도율, 프롬프트 팽창 중 하나일 것).

   | 액션 | 추정 원가(2026-08-14) | 현행 단가 | pro 순수령 |
   |---|---|---|---|
   | 첫 생성 | 1.0~2.3원 | 25토큰 | 15.8원 |
   | 구성 수정 | 1.0원 | 12토큰 | 7.6원 |
   | 모티프 생성 | 12.4원 (최악 19.4원) | 100토큰 | 63.1원 |
   | 실사화 | 2.4~4.8원 | 무과금 (10회/일) | — |
   | 아이디어 | 0.5원 | 무과금 (6회/분) | — |

   추정 원가에는 provider 요금과 Cloud Run 요청 시간이 함께 들어 있다. 실측에서도 두 축을
   분리해 적는다 — provider는 `provider_usage` 로그, Cloud Run은 `generation_jobs`의
   `started_at`/`finished_at`(이미 `admin/generation.py::finalize_duration_seconds()`가 집계)로
   구한다.

4. **재정립** — **스케일(1토큰 ≈ 1원)은 유지하고 단가만 조정한다.** 판단 기준:
   - **평균 원가 ≤ pro 순수령의 25%** 그리고 **최악 원가 < pro 순수령**(단일 요청 적자 없음).
     순수령은 표기가에서 VAT 10%·카드 수수료 3.3%를 뺀 값이고, 여유가 가장 적은 pro로 검사한다.
   - 원가 **비율**을 가격에 그대로 옮기지는 않는다: 원가율이 낮아 원가가 가격을 지배하지 않고,
     디자인 생성은 넥타이 주문의 퍼널이라 생성 횟수를 조이는 것이 더 비싼 선택이다.
   - 모티프 단가는 `gpt_image.py`의 이미지 quality와 `motif_generate_per_request_limit`를
     같이 본다 — 최악 케이스(limit × 장당 원가 + CPU)가 단가 수익을 넘으면 안 된다.
   - 실사화·아이디어는 이제 스케일상 과금이 표현 가능하다(각 3~5토큰, 1토큰). 실측 원가가
     예상을 크게 넘으면 과금을 검토하되, 실사화는 구매 직전 단계라 전환 손실을 함께 본다.
   - 플랜 가격(2,500/6,500/18,000원)과 토큰 수량(2,500/7,500/25,000)은 건드리지 않는다.
     액션 단가만 조정한다 — 플랜 자체를 바꾸는 건 전환율 데이터가 필요한 별개 결정이다.
5. **반영** — `apps/api/scripts/seed.py`의 `ADMIN_SETTINGS` 단가 키와 `docs/api-spec/money.md §6`
   표를 같은 커밋에서 고친다. 운영 DB는 seed가 아니라 **admin 설정 화면**으로 바꾼다(시드는
   신규 환경 기본값). admin 화면의 `defaultValue`·`editWarning` 문구도 같이 맞춘다.
6. **기록** — 결과를 `docs/reviews/token-pricing-recalibration-<날짜>.md`에 남기고 이 플랜을
   삭제한다. 실측 표(operation별 토큰·콜 수·원가)를 그대로 붙여 다음 재정립의 기준선으로 쓴다.

## 같이 볼 것 (실측이 답을 주는 미결 사항)

- **아이디어 제안 무과금 유지 여부**: 6회/분 리미터만 있고 일일 한도가 없다. 실측 원가가
  생성의 절반을 넘으면 과금하거나 일일 한도를 붙인다.
- **RAG 예시 3건의 값어치**: 예시가 입력 토큰의 약 15%다. 예시 수를 2로 줄였을 때
  compile 성공률이 유지되면 그게 가장 싼 절감이다(`eval_authoring.py`로 검증).
- **프롬프트 캐시 적중률**: `cached=`가 0에 가깝다면 시스템+스키마 접두부가 매 콜 달라지고
  있다는 뜻이다. 접두부를 고정하는 것만으로 입력 단가가 내려간다.
- **finalize 실사화(무과금, 10회/일)**: provider 비용은 0이지만 2vCPU·4GiB Cloud Run과 GCS를
  쓴다(회당 2.4~4.8원 추정). Cloud Run 무료 등급이 월 약 3,000회를 흡수하므로 그 볼륨을 넘기
  시작하면 과금 또는 한도 하향을 검토한다. 소요 시간은 이미 `generation_jobs`에 있다.
