# 플랜 문서 하네스

`docs/plans/`에는 **아직 실행하지 않은** 플랜·제안만 둔다. 실행을 완료하면 결과를
`docs/reviews/`에 기록하고 여기서 삭제한다. 이 문서는 플랜을 쓸 때의 형식 규칙이다.

## 독자 전제

플랜의 독자는 "이 문서만 들고 실행하는 미래의 에이전트나 사람"이다. 대화 맥락 없이
실행 가능해야 하며, 그래서 지시서 형식으로 쓴다 — 서술("~하면 좋겠다")이 아니라
지시("~로 바꾼다. 근거는 ~")로.

## 섹션 (순서대로, 해당 없으면 생략)

1. **제목 + 전제** — 무엇을, 어떤 조건에서 실행하는지 첫 문단에. 날짜는 절대 날짜로
   (예: `token-pricing-recalibration.md`의 "2026-08-14에 넣은 로깅이 쌓인 뒤 실행한다").
2. **왜 필요한가** — 문제의 근거. 실측·리뷰 문서 링크로 뒷받침하고, 추측이면 "추정"이라고
   표기한다. 과거에 같은 문제가 왜 생겼는지 알면 그것도 적는다.
3. **범위 밖(non-goals)** — 이 플랜이 하지 않는 것 한두 줄. 범위 논쟁을 문서가 끝낸다.
4. **실행 조건** — 선행 조건과, **실행하면 안 되는 조건**을 명시한다. 조건이 안 차면
   기다린다는 문장까지 포함할 것 (예: "표본이 안 차면 실행하지 말고 기다린다").
5. **절차/항목** — 번호 목록. 각 항목은 `파일:라인` + 무엇을 어떻게 바꾸는지 + 근거
   한 문장. 순위표형 플랜이면 효과 ÷ 난이도 순으로 정렬하고 위에서부터 실행한다.
   각 항목은 독립적으로 실행·검증 가능한 크기로 자른다.
6. **검증** — 성공을 확인하는 구체 명령이나 관찰 (curl, psql, 브라우저 실측 등).
7. **되돌리는 법 / 상향 신호** — 위험한 변경에만. 되돌리는 절차와, 되돌려야 한다는
   신호가 무엇인지 (예: `gcp-cost-reduction-2026-08-17.md`의 "상향 신호" 문단).
8. **기각한 대안** — 고려했다가 버린 안과 이유 한 줄씩. 재론을 막는 게 목적이므로
   기각 사유가 사라지면 재론한다는 조건도 함께.

## 규칙

- 코드 붙여넣기 금지 — `파일:라인` 참조로 충분하다. 코드는 플랜이 실행될 때쯤 바뀌어 있다.
- 외부 사실(과금 정책·API 시맨틱·라이브러리 동작)은 출처를 확인하고 쓴다 — 기억으로
  쓴 단가·기본값이 플랜의 대표적 오류원이다.
- **실패 모드 한 줄** — 이 플랜이 어떻게 잘못될 수 있는지 명시한다
  (예: "추정치를 실측으로 포장하는 게 이 플랜의 실패 모드다").
- `docs/api-spec/` 정본과 달라지는 변경이면 명세 갱신을 플랜 항목에 포함한다 (대원칙).
- 이미 실행된 리뷰(`docs/reviews/`)와 겹치는 항목은 제외하고, 제외했다고 적는다.
