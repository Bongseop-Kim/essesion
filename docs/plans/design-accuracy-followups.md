# 디자인 정확도 — 트리거를 기다리는 두 항목

2026-09-09 [정확도 평가 라운드](../reviews/design-accuracy-baseline-2026-09-09.md)에서 남은 것이다.
그날 확인 가능한 것은 브라우저(Aside)로 직접 재현해 처리했고, 여기 남은 둘은 **더 좁히려면 실제
프로덕션 데이터가 필요하다.** 트리거가 관측되기 전에 여는 것은 근거 없는 변경이다.

## 실행 조건

- 유료 호출은 `--confirm-live`와 명시적 동의가 있을 때만.
- 코퍼스 문장·조건 변경은 사람이 확정한 뒤에만. 실패를 통과시키려고 조건을 고치지 않는다.
  기준값이 필요하면 엔진 안의 근거(예시 `size_ratio` 등)를 찾아 쓰고 출처를 적는다.
- 트리거는 로그·사용자 보고 중 하나로 근거를 남긴 뒤 연다. **"기다린다"고 적어두고 확인하지 않는 것도
  실패다** — 로컬에서 재현 가능한 것은 먼저 재현해 본다(2026-09-09에 이 방법으로 두 건을 고쳤다).

## 1. 첫 저작의 `colors` 형식 실패 (약 4%)

**트리거**: admin 생성 로그에 `authoring_invalid`(422)가 쌓이고, `authoring_validation_errors`에
`colors: color must be #RGB or #RRGGBB`가 반복해서 보이면.

근거: 2026-09-09 같은 요청 30회 중 1회(유효 시도 26회 중 1회, 약 4%) 저작 모델이 `colors` 배열을
잘못된 형식으로 내고 재저작 4회 안에 고치지 못했다. 카탈로그 후보 제공과는 무관하다(그 가설은 기각).
프로덕션은 422 + 환불로 끝나므로 데이터 손상은 없다.

- 열게 되면 **먼저 실패한 값의 실제 형태를 확보한다.** 지금 진단에는 값이 남지 않는다
  (provider 응답 미기록이 설계). admin 로그의 검증 메시지 샘플부터 모은다.
- 값이 "이름 문자열"이면 지명색 접지로, "한 문자열에 여러 hex"면 파싱으로 갈린다 — **형태를 보기 전에
  고치지 않는다.** 추측으로 관대한 파서를 새로 만들지 않는다.
- 저작 시도 횟수를 늘리는 것은 마지막 수단이다(호출 비용이 곧바로 는다).

## 2. 곡선 bbox 정밀화

**트리거**: AI 생성(gpt_image) 모티프가 같은 크기 설정에서 작아 보인다는 실제 불만.

근거: 2026-09-09 실측에서 카탈로그·업로드 모티프는 선언 크기의 0.98~1.00을 채우는데
gpt_image 2건만 0.854·0.947이었다. 같은 크기로 나란히 렌더해 눈으로도 비교했는데, 차이는
bbox 과대추정보다 **형상의 종횡비**가 지배적이었다 — 세로로 긴 그림은 bbox가 정확해도 작아 보인다.

- 고치면 기존 저장 모티프와 신규 모티프의 크기 기준이 갈린다. **identity 이관 계획을 먼저 세운다.**
- 열기 전에 불만이 실제로 bbox 때문인지(같은 종횡비의 catalog 모티프와 비교) 먼저 가른다.

## 검증

- 오프라인: `uv run pytest apps/worker/tests/test_design_accuracy.py apps/worker/tests/test_patch.py`.
- 수집·채점: `collect_design_accuracy.py --confirm-live` → `eval_design_accuracy.py --outputs …`.
  간헐적 실패는 `--repeat N`으로 사례별 성공률을 낸다 — 1회 실행 통과율은 20% 실패도 못 본다.
- 브라우저 확인은 Aside 하네스로, 서버 기동 전 기존 포트를 확인한다. 워커는 `--reload` 없이 띄우면
  옛 코드로 도니 코드를 고친 뒤에는 반드시 재시작한다(2026-09-09에 실제로 걸린 함정).

**실패 모드:** 트리거 없이 열어 근거 없이 고치는 것, 만점 통과율을 품질 보증으로 착각하는 것,
그리고 로컬에서 재현할 수 있는 문제를 "사용자 보고 대기"로 미뤄두는 것이다.
