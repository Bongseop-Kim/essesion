# 주문서: 결제 수단을 보기 전에는 결제 버튼이 스크롤만 하게, 주문 상품 카드 재배치

2026-11-19 운영자 요청으로 작성했다. 모바일 주문서에서 손볼 것은 두 가지다.
(A) 결제 수단을 아직 보지 않은 상태에서 하단 고정 "결제하기"를 누르면, 결제를 시작하지 않고 결제 수단 섹션으로
스크롤한다.
(B) 주문 상품 카드에서 금액이 줄바꿈되어 깨지는("16,/000원") 배치를 고친다.
둘은 서로 독립적이라 따로 실행하고 따로 검증할 수 있다. 선행 조건은 없다.

## 왜 필요한가

- **A** — 모바일에서는 `ContentLayout`이 사이드바(결제 금액 요약 + 토스 결제 위젯)를 본문 아래에 쌓는다
  (`apps/store/src/shared/ui/content-layout.tsx:116-129`). 결제 CTA는 하단 고정 바에 있다(`:130-151`).
  `CheckoutShell`은 위젯이 준비되면 버튼을 바로 활성화하고, 누르면 곧장 `onPay`를 부른다
  (`apps/store/src/features/checkout/ui/checkout-shell.tsx:61-71`). 그래서 사용자는 결제 수단 목록을 한 번도
  보지 않고 결제할 수 있고, 그 경우 위젯의 기본 선택(실시간 계좌이체)으로 결제가 진행된다. 운영자가 실제
  사용 중에 발견했다. 버그는 아니지만 고객이 원하지 않은 수단으로 결제하게 되는 사용성 문제다.
- **B** — `OrderItemCard`(`apps/store/src/pages/order/order-form.tsx:414-488`)는 이름·설명 VStack과 금액을 한
  HStack에 나란히 둔다(`:451-468`). 금액 `Text`에는 줄바꿈 금지도, 축소 금지도 걸려 있지 않다. 그래서 좁은
  화면에서는 금액 칸이 줄어들어 쉼표 뒤에서 줄이 바뀐다. 오른쪽 금액 칸이 폭을 가져가니 설명
  ("자동 수선(지퍼 · 착용자 177cm)")도 두 줄로 밀린다. 결과적으로 이미지(5rem = 80px)보다 텍스트 칸이 훨씬
  높아져 카드 아래쪽이 비어 보인다. 장바구니 카드(`apps/store/src/pages/cart/index.tsx:633-688`)는 이미 금액을
  설명 아래 왼쪽에 두고 이미지를 6rem으로 쓰고 있어 이 문제가 없다.

## 범위 밖

- 토스 위젯의 기본 선택 결제 수단을 바꾸는 일. 토스 상점관리자의 결제 UI 설정에서 바꿀 수 있는지는 확인하지
  않았다. 바꿀 수 있다 해도 "보지 않고 결제한다"는 문제는 그대로 남으므로 이 플랜과 별개다.
- 장바구니 카드의 금액 표기 통일. 장바구니는 `₩16,000`, 주문서는 `16,000원`으로 다르다.
- 데스크톱 레이아웃 변경. 데스크톱은 결제 버튼이 sticky 사이드바의 위젯 바로 아래에 있어 문제가 없다.

## 절차

### A. 결제 수단을 아직 못 봤으면 결제 버튼이 스크롤만 한다

`CheckoutShell` 한 곳에서 처리한다. 이 컴포넌트는 `order-form.tsx`(장바구니 주문)와 `order-payment-page.tsx`
(주문 제작·샘플 결제)가 함께 쓴다. 따라서 결제 화면 세 곳 모두에 같은 동작이 들어간다.

판정은 **버튼을 누른 시점에** 좌표를 한 번 비교하는 것으로 끝낸다. `IntersectionObserver`는 쓰지 않는다(이유는
기각한 대안).

1. `checkout-shell.tsx:41-48` — `PaymentWidget`을 `Box`로 감싸고 ref를 단다. 이 영역에 다음 두 가지를 준다.
   - 스크롤 대상 여백: `scroll-margin-top`을 헤더 높이(`--spacing-x16`, `content-layout.tsx:104`의 sticky
     top과 같은 값)만큼 준다. 그래야 스크롤 뒤에 위젯 윗부분이 헤더에 가리지 않는다.
   - `tabIndex={-1}`: 스크롤한 뒤 이 영역으로 포커스를 옮겨, 스크린리더 사용자도 어디로 이동했는지 알게 한다.
2. `checkout-shell.tsx:52` actionBar의 `VStack`에도 ref를 단다. 버튼을 누를 때 두 영역의
   `getBoundingClientRect()`를 읽어 **"위젯 영역의 바닥 ≤ actionBar의 윗변"**이면 결제 수단이 보이는 것으로 본다.
   - 바 높이는 Callout·helperText 유무에 따라 달라지지만, 누른 시점의 실제 좌표를 읽으므로 따로 계산할 것이
     없다.
   - 데스크톱에서는 actionBar가 위젯 바로 아래에 그려지므로(`content-layout.tsx:107-108`) 이 조건이 항상
     참이다. 동작은 지금과 같고, breakpoint로 분기하지 않는다.
3. "결제 수단으로 한 번 데려갔다" 상태(`paymentSeen`, ref나 state)를 둔다. `checkout-shell.tsx:68`의 `onClick`을
   다음 순서로 바꾼다.
   - `paymentSeen`이 `true`이거나 2번 조건이 참이면 지금처럼 `onPay`를 부른다.
   - 아니면 감싼 영역을 `scrollIntoView({ behavior: "smooth", block: "start" })`로 스크롤하고,
     `focus({ preventScroll: true })`로 포커스를 옮기고, **그 자리에서 `paymentSeen`을 `true`로 바꾼 뒤** 끝낸다.
     `prefers-reduced-motion`이 켜져 있으면 `behavior: "auto"`로 즉시 이동한다.
   - `preventScroll`을 빼면 `focus()`가 즉시 점프해 smooth 스크롤이 끊긴다.
   - 스크롤시킨 클릭에서 바로 latch를 켜는 이유: 위젯(결제 수단 + 약관)이 `화면 − 헤더 − 하단 바`보다 크면
     `block: "start"`로 스크롤한 뒤에도 바닥이 바에 가려 2번 조건이 계속 거짓이다. latch가 없으면 두 번째
     클릭도 같은 자리로 스크롤만 해서 결제를 할 수 없게 된다. 토스 위젯의 실제 높이는 재지 않았다(추정).
   - 한 번 켠 `paymentSeen`은 다시 끄지 않는다. 결제 수단을 고른 뒤 배송지를 확인하러 위로 올라간 사용자를
     결제할 때마다 또 끌어내리지 않기 위해서다.
4. 버튼 문구는 바꾸지 않는다("○○원 결제하기"). 처음 누르면 스크롤만 된다는 점은 화면 이동으로 충분히
   드러난다. 문구를 "결제 수단 선택"으로 바꾸는 안은 아래 기각한 대안에 적었다.
5. 테스트: `apps/store/src/features/checkout/ui/` 옆에 `checkout-shell.test.tsx`를 추가한다. jsdom에는
   `scrollIntoView`가 없고 `getBoundingClientRect`는 0을 돌려주므로 둘 다 목으로 둔다. 다음 세 경우를 확인한다.
   - 위젯 바닥이 바 아래에 있을 때 처음 누르면 `onPay`가 불리지 않고 `scrollIntoView`가 불린다.
   - 좌표가 그대로여도 한 번 더 누르면 `onPay`가 불린다(latch).
   - 위젯 바닥이 바 위에 있으면 처음 눌러도 `onPay`가 불린다.

### B. 주문 상품 카드 재배치

2026-11-19 운영자가 아래 "레이아웃"안을 확정했다. 장바구니 카드와 같은 구조다.

6. `order-form.tsx:441` — 이미지 칸을 `5rem`에서 `6rem`으로 바꾼다. 장바구니(`cart/index.tsx:633`)와 맞추고,
   텍스트 칸(뱃지·이름·설명·금액)과 높이가 비슷해진다.
7. `order-form.tsx:451-468` — 오른쪽 금액 칸을 없앤다. 금액(`OrderItemPrice`)을 설명 바로 아래, 텍스트 칸 안에
   왼쪽 정렬로 둔다. 금액 칸이 차지하던 폭이 돌아와 설명이 한 줄에 들어간다.
8. `order-form.tsx:514-538` `OrderItemPrice` — 할인이 있을 때 쓰는 `VStack alignItems="flex-end"`를 바꾼다.
   장바구니 `ItemPriceDisplay`(`cart/index.tsx:740-770`)처럼 취소선 원가와 할인가를 `HStack wrap`으로
   나란히, 왼쪽 정렬로 둔다. 금액 `Text`는 쉼표 사이에서 줄이 바뀌지 않도록 `white-space: nowrap`으로 줄바꿈을 막는다. 금액이 길어지면
   숫자 안이 아니라 원가와 할인가 사이에서 줄이 바뀐다.
9. `order-form.tsx:469-483` — 쿠폰 행을 Grid 밖으로 빼서 카드 전체 폭을 쓰게 한다. 왼쪽에 "적용된 쿠폰
    없음"(또는 "○○ 적용"), 오른쪽에 ghost "쿠폰 변경" 버튼을 둔다. 쿠폰 이름이 길어도 이미지 칸 폭만큼 여유가
    생긴다. Grid와 쿠폰 행 사이 간격은 `x3`으로 한다.

## 레이아웃 (B, 확정)

모바일 390px 폭 기준이다. 카드 안쪽 폭은 약 326px이다. 금액을 설명 아래로 옮기고, 쿠폰 행은 카드 전체
폭으로 둔다.

```
┌────────────────────────────────────┐
│ ┌────────┐  [수선]                 │
│ │        │  넥타이 수선            │
│ │  사진  │  자동 수선(지퍼·177cm)  │
│ │  96px  │  16,000원               │
│ └────────┘                         │
│ 적용된 쿠폰 없음         쿠폰 변경 │
└────────────────────────────────────┘
할인 시 금액 줄:  ~~16,000원~~ 14,400원  (공간이 모자라면 원가와 할인가 사이에서 줄바꿈)
```

## 검증

- `pnpm lint && pnpm --filter store typecheck && pnpm --filter store test`
- `e2e/store-money-path.spec.ts:86`은 `Desktop Chrome` 뷰포트로 결제 버튼을 한 번 누른다
  (`playwright.config.ts`의 `store-chromium`). 데스크톱에서는 2번 조건이 항상 참이므로 그대로 통과해야 한다.
  실패하면 2번의 가정이 틀린 것이니 원인을 확인한다. 클릭을 두 번으로 바꿔서 덮지 않는다.
- 모바일 실기기(또는 DevTools 390×844)에서 다음을 확인한다. 이 확인은 사용자가 띄워 둔 서버에서 한다.
  1. 주문서 첫 화면에서 결제하기를 누르면 결제 수단 섹션으로 부드럽게 스크롤되고, 결제창은 뜨지 않는다.
  2. 그 상태에서 다시 누르면 결제가 진행된다. 화면이 작은 기기(예: 375×667)에서도 확인한다. 위젯 바닥이
     바에 가려 있어도 두 번째 클릭은 결제여야 한다.
  3. 직접 스크롤해 결제 수단과 약관이 바 위로 다 보이는 상태에서 처음 누르면 바로 결제가 진행된다.
  4. 한 번 스크롤된 뒤 맨 위로 돌아와 누르면 다시 끌려 내려가지 않고 결제가 진행된다(latch).
  5. 상품 카드에서 금액이 한 줄로 보이고, 할인 쿠폰을 적용했을 때 원가와 할인가가 깨지지 않는다.
- 주문 제작·샘플 결제(`order-payment-page.tsx`)에서도 1·2를 같은 방식으로 확인한다.

## 기각한 대안

- **버튼 문구를 상태에 따라 바꾸기**("결제 수단 선택" → "○○원 결제하기"): 금액이 처음부터 보여야 한다는 요구와
  충돌하고, 문구가 바뀌면서 바의 레이아웃이 흔들린다. 스크롤 동작만으로 의도가 전달되지 않는다는 신호(같은
  위치에서 버튼을 연달아 누르는 패턴 등)가 보이면 다시 검토한다.
- **결제 수단을 본문 위쪽(배송지 아래)으로 옮기기**: 금액 요약보다 결제 수단이 먼저 나와 읽는 순서가 어색해진다.
  `ContentLayout`의 사이드바 계약(`sidebarFirst`)도 손대야 해서 영향 범위가 커진다.
- **매번 "현재 보이는지"만 보고 판정하기(latch 없음)**: 결제 수단을 고른 뒤 위로 올라간 사용자를 결제할 때마다
  다시 끌어내린다. 위젯이 화면보다 크면 아예 결제를 할 수 없게 된다.
- **`IntersectionObserver`로 "본 적 있음"을 미리 기록하기**: 직접 끝까지 스크롤해 보고 맨 위로 돌아온 사용자를
  한 번도 끌어내리지 않는 장점이 있다. 하지만 `rootMargin`은 생성할 때 고정이라, Callout이 떠서 바 높이가
  바뀌면 observer를 다시 만들어야 한다. 콜백이 비동기라 e2e 클릭과 경합할 여지도 생긴다. 그 사용자는 지금
  안에서도 한 번만 스크롤되고 끝난다. "봤는데 왜 또 내려가느냐"는 불만이 들어오면 passive scroll 리스너로
  같은 좌표 비교를 미리 해 두는 방식을 검토한다.
- **(B) 금액은 오른쪽에 두고 줄바꿈만 막기**: 가장 작은 수정이지만, 설명이 금액 칸에 밀려 두 줄이 되고 사진과
  글자 칸의 높이 불균형이 그대로 남는다. 할인가가 붙으면 오른쪽 칸이 더 넓어진다.
- **(B) 금액을 카드 맨 아래 합계 행으로 내리기**: 금액은 가장 잘 보이지만, 카드가 높아지고 장바구니 카드와
  구조가 달라진다.

실패 모드: 스크롤시킨 클릭에서 latch를 켜지 않는 경우다. 위젯이 화면보다 큰 기기에서 결제 버튼이 계속
스크롤만 하고 결제가 되지 않는다. 돈 경로가 막히는 것이라, 원래 고치려던 사용성 문제보다 훨씬 나쁘다.
