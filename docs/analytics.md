# 스토어 계측 — 왜 붙였고 무엇을 보는가

> 나중에 "이거 뭐하려고 켰더라" 할 때 읽는 문서. 설치 절차는 여기 없다 —
> 실행 지시는 [계측 플랜](plans/analytics-posthog.md)에 있다.

## 현재 상태 (2026-08-19)

| 도구 | 상태 | 무엇 |
|---|---|---|
| **Sentry** | 가동 중 | 프론트 에러. `apps/store/src/shared/lib/observability.ts` |
| **GA4** | **가동 중** (2026-08-14~) | 측정 ID `G-1V993D3825`. `apps/store/src/shared/lib/analytics.ts` |
| **PostHog** | **미도입** | 콘솔 프로젝트만 생성됨 |

## 왜 두 개나 쓰나

한 줄로: **GA4는 "어디서 왔나", PostHog는 "와서 뭘 하다 갔나"**를 본다. 둘 다 방문자 수를
세지만, 그건 겹치는 부분이지 쓰는 이유가 아니다.

| | GA4 | PostHog |
|---|---|---|
| 답하는 질문 | 어느 채널·광고·검색어로 들어오나 | 어느 화면에서 막히나, 이 사람이 뭘 눌렀나 |
| 고유 기능 | Google Ads·Search Console 연동, 무료 무제한 | **세션 리플레이**, 퍼널, 코호트 리텐션 |
| 비용 | 무료 | 무료 한도: 월 100만 이벤트 / 5,000 리플레이 |
| 보는 단위 | 집계(비율·추이) | 개인(한 사람의 여정) |

**경계를 지키는 게 핵심이다.** PostHog로 채널 리포트를 만들기 시작하거나 GA4에 제품 이벤트를
더 얹기 시작하면, 같은 걸 두 번 유지하는 상태가 된다. 그 순간 하나를 버리는 게 맞다.

## PostHog을 굳이 넣는 진짜 이유

이 서비스에서 가장 안 보이는 곳은 **디자인 생성 화면**이다. GA4가 받는 건
`generate_design { rejected: 0|1 }` 하나뿐이고, 프롬프트 원문은 개인정보 정책상 일부러 안 보낸다.
그래서 GA4로는 **"거절률 몇 %"까지만** 알 수 있다.

정작 알고 싶은 것 — 사용자가 프롬프트를 몇 번 고쳐 쓰다 포기했는지, 어느 버튼을 못 찾았는지 —
는 리플레이 한 편이면 보이고 GA4로는 영원히 안 보인다. **리플레이를 안 볼 거면 PostHog을 넣을
이유가 없다.**

## 무슨 질문 → 어디서 보나

| 알고 싶은 것 | 어디 |
|---|---|
| 이번 달 방문자, 어제 대비 | GA4 > 보고서 > 실시간/획득 |
| 인스타 광고가 실제로 사람을 데려왔나 | GA4 > 획득 > 트래픽 획득 (UTM 기준) |
| 검색으로 들어온 사람은 뭘 검색했나 | GA4 > 라이브러리 > Search Console 컬렉션 (**게시해야 보인다**) |
| 상품 보고 장바구니까지 몇 %가 가나 | PostHog > 퍼널 |
| 디자인 만들다 왜 나가나 | **PostHog > 세션 리플레이** |
| 결제하다 어디서 튕겼나 | PostHog 리플레이 + Sentry 에러 |
| 실제 매출·주문 건수 | **둘 다 아님 — DB가 정본** |

## 지금 계측되는 이벤트

`apps/store/src/shared/lib/analytics.ts`의 `GaEvents`가 정본. 호출부는
`grep -rn "trackEvent(" apps/store/src`.

| 이벤트 | 발화 지점 |
|---|---|
| `login` | 로그인 성공 (password / oauth) |
| `view_item` | 상품 상세 진입 |
| `add_to_cart` / `add_to_wishlist` | 상품 상세 버튼 |
| `begin_checkout` | 결제 시작 |
| `purchase` | 결제 성공 페이지 |
| `token_purchase` | 토큰 구매 성공 |
| `generate_design` | 디자인 생성 (거절 여부만) |
| `quote_request` | 맞춤 주문 견적 요청 |

페이지뷰는 SPA라 자동이 아니다 — `app-layout.tsx`가 라우트 변경 시 직접 쏜다. 쿼리스트링은
빼고 보낸다(OAuth code·paymentKey 유출 방지).

**이벤트를 늘리기 전에 한 번 더 생각할 것**: PostHog autocapture가 켜지면 클릭·폼 제출은
설계 없이 자동으로 쌓인다. 손으로 정의한 이벤트는 이름을 영원히 유지해야 하는 부채다.

## UTM 표기 규칙

**광고 계획: 2026년 10~11월경, 채널 미정.** 채널이 정해지기 전이라 `utm_source` 값 목록은
비워둔다 — 안 쓸 값을 미리 정해봐야 그때 가서 다시 정하게 된다.

대신 **형식만** 지금 고정한다. 이유는 하나: 표기가 흔들리면(`instagram` vs `Instagram` vs
`insta`) GA4가 같은 채널을 여러 줄로 쪼개서 보여주고, **이건 사후에 못 고친다.**

- **전부 소문자, 공백 없음, 하이픈으로 잇는다.**
- `utm_medium`은 아래 넷 중에서만 고른다 — 새로 만들지 않는다.
  `cpc`(유료 클릭) / `social`(무료 게시물) / `email` / `referral`
- `utm_campaign`은 **연월 + 짧은 이름**: `2026-11-launch`.

### 첫 광고를 돌리기 전에 할 것

`utm_source` 값을 정해서 **아래 표에 먼저 적고, 그 다음 링크를 만든다.** 링크부터 만들면
표기가 갈린다.

| `utm_source` | 어디 |
|---|---|
| _(채널 확정 후 채운다)_ | |

## 숫자를 믿으면 안 되는 지점

1. **매출·주문 건수는 DB가 정본.** `purchase`는 브라우저에서 쏘는 이벤트라 애드블록·결제 직후
   이탈로 유실된다. GA4/PostHog의 매출 숫자는 **추이와 비율을 보는 용도**이지 회계 숫자가 아니다.
2. **GA4 데이터 보존은 기본 2개월.** 표준 집계 보고서(방문자 수·채널별 추이)는 영향이 없지만,
   **탐색(Explore)·퍼널·사용자 단위 분석에 쓰이는 세부 데이터가 2개월 뒤 삭제된다.** 14개월로
   바꿔두지 않으면 "지난 분기에 이 사람들이 어떻게 움직였나"를 나중에 못 판다. 계측이
   2026-08-14에 시작됐으므로 **2026-10-14 전후로 8월분 세부 데이터가 지워지기 시작한다.**
   (관리 > 데이터 설정 > 데이터 보존, 출처: <https://support.google.com/analytics/answer/7667196>)
3. **애드블록 차단분은 두 툴 모두에서 안 보인다.** 두 툴의 방문자 수가 서버 로그보다 항상 적다.
4. **직접 방문(direct)이 많다면 대개 UTM 누락이다.** 진짜 직접 방문이 아니라 표기를 안 붙인 링크다.

## 볼 주기

- **주 1회, 5분** — GA4 획득 리포트에서 유입 채널만. 광고를 돌리는 동안만 의미가 있다.
- **뭔가 이상할 때** — PostHog 리플레이. 정기적으로 볼 것이 아니라, 이탈률이 튀거나 문의가
  들어왔을 때 그 사람의 세션을 찾아본다. 이게 리플레이의 정상 사용법이다.
- **월 1회** — PostHog 사용량이 무료 한도에 얼마나 근접했는지.

대시보드를 새로 만들고 싶으면 먼저 **"이걸 누가 언제 여나"**에 답한다. 답이 없으면 만들지 않는다.

## 개인정보 원칙 (타협 없음)

- **이벤트에 PII를 넣지 않는다** — 프롬프트 원문, 연락처, 주소, `paymentKey`·`orderId` 원문,
  URL 쿼리스트링. `analytics.ts` 최상단 주석이 이 규약의 정본이다.
- **세션 리플레이는 배송지·연락처를 마스킹한 뒤에만 켠다.** 입력창은 PostHog이 기본 마스킹하지만
  **화면에 텍스트로 표시된 주소·연락처는 마스킹되지 않는다.** 주문 확인 화면과 마이페이지가
  그 대상이다.
- 애매하면 가리는 쪽으로 기운다. 리플레이에 안 찍혀서 아쉬운 것과 남의 주소가 외부 서비스에
  남는 것은 비교 대상이 아니다.
