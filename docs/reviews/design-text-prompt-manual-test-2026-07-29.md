## 확인된 원인

- 후보 선택 상태가 `candidateId`만 비교했다. 서로 다른 실행에서 같은 ID가 재사용되면 새 후보를 이미 선택한 것으로 오인해 선택 API를 호출하지 않았다.
- 화면의 후보 수가 성공 후 4로 초기화됐지만 실제 요청과 중복 제거 결과가 섞여, 설정값과 결과 안내가 일관되지 않게 보였다.
- refine 보존 가드는 요청하지 않은 범주는 복원했지만, 색상·간격처럼 명시한 범주가 실제로 변경됐는지는 검사하지 않았다.
- 과거 후보 선택 금지는 프론트와 API 양쪽의 의도된 선형 대화 정책이었다. 과거 후보를 활용할 별도 분기 흐름은 없었다.
- 자동 간격 보정 등 사용자가 조치할 수 없는 워커 경고까지 일반 Callout으로 노출돼 실제 해결 방법을 전달하지 못했다.

## 후속 결정

- 선택 상태를 `(runId, candidateId)`로 식별한다.
- 과거 후보는 현재 대화를 되감지 않고 새 대화로 분기한다.
- 후보 수는 대화별 마지막 제출값을 유지하고 새 대화만 4개로 시작한다.
- 사용자에게는 부분 생성과 인쇄 색역처럼 조치 가능한 안내만 최대 한 건 노출한다.
- 명시한 색상·모티프·기하·스트라이프 변경이 없으면 저작을 재시도한다.
- 스트라이프의 정확한 두께와 밴드 수를 수치적으로 강제하는 개선은 별도 후속 과제로 둔다.

### 후속 개선 반영 (같은 날, 최종안으로 대체)

1차 개선(입력창 위 수정 기준 칩 + 분기 안내 캡션)을 적용했다가, "칩이 공간을 과하게 차지하고 과거 타일 클릭이 여전히 즉시 분기한다"는 피드백으로 같은 날 아래 최종안으로 대체했다. 서버 계약(select=최신 런만, 과거 후보는 branch)은 변경 없음.

- **클릭=조회 전용**: 과거 런 타일 클릭이 즉시 세션 분기하던 동작을 제거. 클릭은 좌측 패널에 조회 스테이징만 하고(제목 "이전 결과 미리보기"), 포인터 이동은 명시적 "이 이미지로 편집" 버튼으로만 실행한다. 모바일 과거 타일은 앵커 메뉴(미리보기·이 이미지로 편집)로 동일 규칙. 최신 런 타일 클릭=선택(포인터 이동)은 유지 — select는 무료·가역이다.
- **체크 → [편집중] 배지**: 선택 타일의 체크 원형을 `Badge`(brand solid) "편집중"으로 교체(`candidate-grid.tsx`). 입력창 근처 별도 표시가 없어졌으므로 모바일에서도 노출한다. 입력창 위 수정 기준 칩(`edit-basis-chip.tsx`)은 제거.
- 과거 런 캡션 문구를 조회 의미로 교체: "이전 결과예요. 후보를 누르면 미리보기로 확인할 수 있어요." 접근성 라벨도 "이전 결과 보기"로 변경.
- 재검증(Aside, PC): 과거(포인터) 타일 클릭 시 분기 없음 → 최신 후보 선택 시 배지 이동 → 과거 타일 클릭 시 패널 전환 + "이 이미지로 편집"/"미리보기 닫기" 노출 → 닫기 복귀 → 명시적 편집 클릭 시에만 새 세션 분기(스낵바 확인). 콘솔 오류 없음. `pnpm --filter store test`(237개)·`typecheck`·`pnpm lint` 통과.

### "이 이미지로 편집" = 같은 대화의 정본 커밋으로 변경, 분기 UI 제거 (같은 날)

"이 이미지로 편집이 새 세션을 만드는 건 잘못 — 텍스트 입력의 기준으로 넘기는 용도이고, 새 대화는 새로 만들기(+)가 유일한 창구"라는 피드백 반영.

- 서버: select의 "최신 런만 허용"(409 `stale_design_selection`) 제약을 "이 세션의 성공 런이면 허용"으로 완화. 다른 세션의 런은 409 `design_result_unavailable`. 과거 후보 선택은 이력을 되감지 않고 `current_intent`만 교체하며, 다음 생성 완료 시 자동 커밋이 포인터를 최신으로 되돌린다(명시 지정 1회 유지 규칙이 추가 상태 없이 성립).
- 클라이언트: "이 이미지로 편집"이 branch 대신 기존 select 플로우를 호출. `useDesignBranch`와 분기 UI 경로를 전부 제거(새 대화는 "새로 만들기"만). 버튼 위계도 기본 액션과 동일한 레벨(neutralWeak)로 통일 — brandSolid 단독 강조가 어색하다는 피드백 반영.
- 서버의 branch 엔드포인트 자체는 남아 있다(웹 UI 미사용). 모바일 계획에도 없다면 제거 후 codegen 재생성이 후속 과제.
- 검증: `test_select_accepts_past_run_within_session_only` 추가 포함 design API 테스트 72개·ruff·pyright 통과, store 테스트 237개·typecheck·lint 통과. 브라우저에서 과거 후보 조회→"이 이미지로 편집" 시 같은 대화에 남은 채 배지만 해당 후보로 이동하는 것을 확인했다(콘솔 오류 없음). 플랜 문서 판정 원칙·C10을 새 계약으로 갱신.

### 클릭=조회 전면 통일·패널 액션 상시화 (같은 날)

추가 피드백 3건 반영. 서버 변경 없음(클라이언트만).

- 최신 런 타일 클릭이 즉시 select(포인터 이동)하던 예외를 제거 — **모든 타일 클릭은 신구 구분 없이 조회 스테이징만** 하고, 커밋은 "이 이미지로 편집"으로 통일했다. `TurnFeed`의 최신/과거 런 구분(`latestSelectableRunId`)·과거 런 캡션·라벨 분기·이중 메뉴가 전부 삭제됐고, 모바일 메뉴는 [미리보기·이 이미지로 편집·내려받기·다시만들기·실사화하기] 하나로 합쳐졌다.
- 다시만들기·내려받기·실사화하기는 **상시 노출**로 변경. "이 이미지로 편집"은 미리보기가 편집 대상이 아닐 때만 같은 줄 맨 앞에 나타난다. "미리보기 닫기" 버튼은 제거 — 편집 대상 타일을 다시 누르면 조회가 해제된다.
- 패널 버튼 4종의 배경을 전부 neutralOutline으로 통일 — weak 회색 채움(이 이미지로 편집·다시만들기)이 outline 버튼 옆에서 비활성처럼 오독된다는 피드백 반영.
- 편집 대상 전환 시 3버튼 깜빡임 수정: 낙관적 선택이 intent를 null로 두는 짧은 구간에 `selected`가 false로 떨어져 버튼이 disabled로 점멸하던 것을, 후보가 잡혀 있으면 켜진 상태를 유지하도록 변경(`selected: intent || candidate`). 액션 줄 교체(마운트/언마운트)도 사라져 점멸 요인 자체가 제거됐다.
- 검증: store 테스트 237개·typecheck·lint 통과. 브라우저에서 최신 후보 클릭→포인터 불변·"후보 미리보기" 전환·4버튼 공존, 커밋 시 배지 이동·편집 버튼만 소멸, 편집 대상 재탭 시 조회 해제를 확인(콘솔 오류 없음).

참고: 세션 첫 생성이 `intent_invalid`로 실패한 뒤 재시도에서 성공하는 패턴이 서로 다른 계정·세션에서 2회 재현됐다. 저작 안정성 이슈로 별도 확인 필요 → 아래 재검증 원인 진단에서 규명.

### 원인 1 — 색상 요청 미반영 (A2)

모델(gemini-2.5-flash-lite)이 "배경은 버건디, 벌은 아이보리"에 새 hex를 도입하지 않고 기존 팔레트를 셔플했다. 오늘 버건디 요청 4회 중 3회가 이 패턴(01:04 `19dd1da5`는 navy를 ground로 셔플)이고 01:07 `96091a38` 한 번만 `#800000`+흰색으로 근사 성공 — 순수 확률이다.

이것이 통과되는 이유는 가드의 구멍이다. `_ensure_requested_refine_changes`(worker `adapters/gemini.py`)는 "colors가 뭐라도 바뀌었나"만 검사하므로 ground 인덱스 셔플도 색상 변경으로 통과한다. 요청한 색이 실제 팔레트에 등장하는지 보는 의미 검증은 없다.

부수 발견: `_COLOR_WORDS`에 버건디·아이보리·금색·은색 등이 없다. 이번엔 "색상"으로 권한이 열려 무관했지만, "배경은 버건디로 바꿔줘"처럼 색이름만 쓰면 색 변경 권한 자체가 열리지 않아 팔레트가 통째로 복원되는 잠재 결함이 있다.

### 원인 2 — 간격 변경 거부 후 구조 손실 (A3)

실패 런의 내부 4회 저작 시도 전부 `lattice drop does not close on the torus (needs (tile/cell)*drop_fraction integer for drop_axis 'column')`. half-drop 사용 시 drop축 개수가 짝수여야 한다는 엔진 제약(`engine/validate.py`)이 DesignPlanV3 스키마에도 프롬프트에도 표현돼 있지 않아, 모델이 간격을 넓히며 홀수 열을 뽑으면 사후 거부만 된다. 재시도 피드백 오류문이 엔진 좌표계 용어(tile/cell/drop_fraction — 플랜에 없는 필드)라 모델이 "columns를 짝수로"로 번역하지 못하고 반복 실패했다. 2차 성공도 실은 drop을 제거해 제약을 우회한 것이다. 컴파일러에는 wave wavelength snap 선례가 있으나 lattice drop은 snap하지 않는다.

### 원인 3 — 스트라이프 추가 전멸 (A5)

3회 요청 × 내부 4 attempts = 12회 전부 원시 응답 파싱 단계에서 `every declared motif must be used and motif indexes must be dense`로 거부됐다. 커밋 플랜과 동일 조건의 라이브 재현으로 방아쇠를 확정했다:

- 대화 히스토리 **없이** 호출 → 2/2 유효한 plan(모티프 유지 + 스트라이프 2줄 추가).
- 실제 요청과 동일하게 히스토리 5건 포함 → 즉시 실패 재현. colors가 `["#DAA520','#000000','#FFFFFF"]` 한 문자열로 깨지고 밴드 커버리지 상한(0.75) 초과 등 구조화 출력 자체가 붕괴.

즉 히스토리가 붙으면 flash-lite의 constrained decoding 품질이 급락한다. 증폭 요인: (a) "두 줄만 추가"에도 전체 plan 재저작을 요구(패치 금지 계약)해 모티프 선언–사용 불일치가 생기기 쉽고, 병합 로직(`_merge_layer_categories`)이 구제하기 전 파싱에서 죽는다. (b) 재시도 피드백이 pydantic 원문 덤프라 교정 신호로 기능하지 못한다.

### 공통 구조 요인과 후속

refine이 약한 모델에게 전체 재저작을 맡기면서, 스키마가 표현 못 하는 엔진 제약은 사후 거부 + 원문 오류 피드백에만 의존하고, 색 요청 반영 여부의 의미 검증이 없다. 결정론적으로 처리 가능한 것(lattice 짝수 보정, 히스토리 절제, 색 반영 검증, 오류문 번역)을 모델 운에 맡기고 있다.

개선 플랜은 아래 "저작 안정화 반영"으로 같은 날 구현·제거됐다. A1–A5 수동 재실행이 남은 검증이다.

### 저작 안정화 반영 (같은 날)

`docs/plans/design-refine-authoring-stability.md`의 1–4번을 구현하고 플랜 문서를 제거했다. 워커만 변경, API 스펙 변화 없음(codegen 불필요).

1. **lattice half-drop 짝수 보정** — `authoring/schema.py` `LatticePlacementPlan`에 after-validator를 추가해 drop축 개수가 홀수면 올림 보정(`n += n % 2`). 갤러리 예시 5건은 전부 이미 짝수라 골든 영향 없음. A3 계열의 torus 거부가 스키마 단계에서 소멸한다.
2. **refine 히스토리 절제** — `_build_prompt`가 refine에서 히스토리를 최근 2건으로 자른다(초기 저작은 6건 유지).
3. **색상 의미 검증** — `_ensure_requested_refine_changes`가 hex 집합이 그대로인 순열 응답(ground 인덱스 셔플 등)을 recolor로 인정하지 않고 재시도시킨다(고정 팔레트는 제외). `_COLOR_WORDS`에 버건디·아이보리·와인·마룬·골드·실버·카키·올리브·민트·크림·차콜(+영문)을 보강 — 색이름만 쓴 프롬프트("배경은 버건디로 바꿔줘")가 색 권한 대신 모티프 교체 휴리스틱으로 새던 잠재 결함도 함께 막힌다. 알려진 한계: 기존 팔레트 색으로의 재배정 요청("별을 검정으로")은 위양성 재시도 1회를 유발할 수 있다.
4. **재시도 피드백 번역** — pydantic 원문 덤프 대신 `계약.필드: 메시지` 한 줄 요약(최대 6줄)과 알려진 실패의 plan 언어 힌트(모티프 선언-사용, hex 문자열 형식)를 되돌린다.

검증:

- 단위: 짝수 보정(+compile→`validate_intent` 통과), 순열 거부 재시도, 색이름 권한 개방, 히스토리 절제, 피드백 번역 테스트 추가. `uv run pytest` worker 492·api 637 통과, ruff·pyright 클린.
- 라이브 측정(A4 커밋 플랜 + A5 프롬프트, flash-lite): 수정 전 히스토리 5건 포함 시 첫 응답부터 colors 배열 붕괴가 재현되던 조건에서, 절제 후 첫 시도 8/10 유효. 남은 실패 2건도 밴드 커버리지 위반(자명한 피드백으로 재시도 회복 가능 유형)뿐.
- 라이브 측정(A2 버건디, 전체 재시도 루프): 5회 중 4회가 1차 순열 거부 → 2차에서 ground `#800000` 도입으로 성공(attempts=2), 1회는 4시도 후 명시 거부(환불 경로). 수정 전 실측 3/4이 조용한 오답 성공이던 것과 대비된다.

A1–A5를 처음부터 다시 실행해 이 문서에 기록하는 것이 남은 검증이다.

## C2 재명세 의도 소거 진단과 refine 복원 정책 재설계 (같은 날)

C2 프롬프트(꿀벌+원 재명세)가 두 런(`871f678a`, `f626aa8f`)에서 전혀 반영되지 않았다. 두 런 모두 C1 스트라이프 세션(`584c50ab`)에서 이어 실행돼 refine 모드로 처리됐고(플랜 문서 5장의 "독립 새 세션" 절차 위반), 그 조건에서 실재 결함이 드러났다.

### 원인

카탈로그 검색(후보 2건)과 LLM 저작(꿀벌+원 플랜)은 모두 성공했으나, 보존 가드가 결과를 폐기했다. `_refine_permissions`의 `_CHANGE_WORDS`가 명사구 재명세("…를 번갈아 배치한 … 패턴")와 금지형("넣지 마")에서 변경 동사를 하나도 찾지 못해 전 범주 권한이 False가 됐고, "승인되지 않은 범주는 전부 복원" 정책이 모델의 motifs·layers를 커밋된 C1 스트라이프 플랜으로 덮어썼다(`preserve_restored_sections: ["motifs","layers"]`). 사용자는 안내 없이 직전 디자인을 5토큰에 다시 받았다.

### 수정 (worker만, API 스펙 변화 없음)

복원 기준을 기본 거부에서 언급 기반 기본 허용으로 재설계했다. 변경 동사 감지(`_refine_permissions`)는 "요청한 변경이 실제 반영됐는지" 검사(`_ensure_requested_refine_changes`) 전용으로 남기고, 복원 여부는 새 `_refine_restore_permissions`가 결정한다:

- 프롬프트가 **언급한 범주**는 모델 결과를 신뢰하고, **명시적 "유지/그대로"** 범주만 커밋 플랜에서 복원한다. 표적 수정("색상만 바꿔줘")에서 무언급 범주 복원은 유지된다.
- 모티프 주제는 열린 어휘("꿀벌과 원")라 단어 매칭 외에 **카탈로그 검색 적중**(`public_catalog_available`)을 모티프 언급 신호로 쓴다.
- 아무 범주도 언급하지 않은 자유 발화("더 고급스럽게")는 전부 복원하면 유료 no-op이 되므로 모델 플랜을 그대로 신뢰한다.

알려진 한계: (a) 카탈로그에 없는 주제를 "모티프" 단어 없이 세션 안에서 재명세하면(C4류) 여전히 복원될 수 있다 — 새 세션 경로는 무관. (b) C2류 재명세에서 모델이 base와 동일한 플랜을 반환해도 ensure가 강제 재시도하지 않는다(변경 동사 기반).

### 검증

- 단위 3종 추가: 재명세 2변형(모티프 단어 유무), 금지형 스트라이프 제거, 자유 발화 신뢰. 기존 A2–A5 권한·복원 테스트 무손상.
- `uv run pytest` 1163 통과, ruff·pyright 클린.
- 라이브 재현(로그 `871f678a`의 커밋 플랜 + C2 프롬프트 + 대화 히스토리, flash-lite) 2/2 PASS — catalog_1·catalog_2 모티프 유지, 스트라이프 레이어 없음, `restored: []`.

수동 재검증 전 worker 재시작이 필요하다(`--reload` 미사용).

## C2 신규 세션 재실행 실패: 모티프 recolor 슬롯 수 위반의 사후 거부 (같은 날)

refine 복원 재설계 후 C2를 절차대로 새 세션에서 재실행하자 두 번 연속 `intent_invalid` 전체 실패(`400bc9df`, `17d2d034`). refine 가드와 무관한 initial 경로의 별개 결함이다.

### 원인

저작·모티프 해석은 전부 성공했다(플랜 3개 validated, 꿀벌·원 exact_token 매칭). "두 모티프는 아이보리와 금색으로 구분" 요청에 flash-lite가 slot_count=1 안내를 무시하고 어느 모티프 레이어에 `color_indices` 2개를 배정했는데, 이 계약 위반을 검사하는 곳이 저작 재시도 루프 **밖**인 해석 후 색 바인딩(`_bind_resolved_motif_colors`)뿐이라 `motif recolor count must match resolved slot count (2 != 1)`로 요청 전체가 거부됐다. 컴파일러는 카탈로그 후보의 `slot_count` 메타데이터를 받고 있으면서도 길이를 검사하지 않았다.

### 수정 (worker만, API 스펙 변화 없음)

`compile_design_plan_v3`가 카탈로그 후보의 `slot_count`를 `_ResolvedMotifSource`로 전달받아, `color_indices` 길이가 어긋나는 플랜을 컴파일 단계에서 `PlanCompileError`로 거부한다. 위반 플랜만 탈락하고(나머지 플랜은 진행) 부족하면 plan 언어 피드백("color_indices must contain exactly N entries, or omit …")으로 재시도된다. slot_count를 모르는 소스(exact input·generate)는 기존 바인딩 검사가 백스톱으로 남는다.

### 검증

- 컴파일러 단위 테스트 추가(위반 거부·정상 통과·메타데이터 부재 시 백스톱 위임). `uv run pytest` 1164 통과, ruff·pyright 클린.
- 라이브 재현(C2 프롬프트 + slot_count=1 후보 2건, flash-lite) 2/2 PASS — 1회차는 attempts=2로 1차 위반이 컴파일 피드백으로 교정됐고(기존 코드라면 전체 실패), 2회차는 attempts=1 즉시 통과. 세 플랜 모두 꿀벌+원 유지, recolor 길이 1.

수동 재검증 전 worker 재시작이 필요하다.
