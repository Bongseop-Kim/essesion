# 주문 제작 구매·견적 병행, 견적 요청 페이지, 포인트 주문 제한, 관리자 사양 표시 — 실행 결과 (2026-11-18)

플랜 세 개(`store-action-bar-quote-always`, `admin-custom-option-pairs`, `point-order-option-limits`)를 브랜치
`feat/custom-order-quote-and-point`에서 실행했다. 제작 기간 문구도 같은 날 운영자 확인 뒤 실행해 남은 플랜은 없다.

## 한 일

- **주문 제작 액션 바**: 100개 이상 자동 견적 전환을 없애고 상품 상세와 같은 한 줄 배치로 바꿨다 —
  견적서 메일(아이콘) · 구매하기(세컨더리) · 견적하기(프라이머리). 수선 장바구니 버튼에 아이콘을 붙였다.
- **견적 요청 페이지** `/custom-order/quote`: 주문서의 "견적하기"가 사양·참고 이미지·예상 금액을 들고 넘어온다.
  연락처는 회원 정보로 채우고(없으면 빈칸) 배송지를 고른 뒤 접수한다. 주문서에서 견적 연락처·배송지 칸과
  "견적을 요청할까요?" 확인 창을 지웠다.
- **100개 이상 구매**: 막지 않고 확인 창으로 견적(생산 일정 확인·계좌이체·세금계산서)을 권한다.
- **견적 최소 수량** 100 → 4(서버 + `docs/api-spec/domains.md`).
- **임시 저장·결제 초안에서 연락처 제거**, 저장 키 `v4`. 견적 초안 스키마(`parseCustomQuoteDraft`)를 따로 뒀다 —
  견적의 참고 이미지는 `object_key`, 결제는 `upload_id`라 모양이 다르다.
- **정보 탭 견적서 섹션**: 가격 섹션 다음. 버튼은 캡처가 아니라 실제 버튼(`EstimateMailButton`)을 그리고, 견적서는
  운영자가 찍은 캡처를 잘라 넣었다(`estimate-sample-2026-11-18.webp`, 입금 계좌 줄 제외).
- **포인트 주문 제한**: 자수·필름을 켜면 주문서가 심지·사이즈·폭·봉제 옵션 칸을 숨기고 서버로는 선택 안 함으로 보낸다.
  원단 직접 제공과 함께 고르지 못한다. 서버는 포인트 주문에 울 심지·bool 7종이 오면 `invalid_options`로 거절한다
  (`docs/api-spec/money.md` §3). 단계 번호는 보이는 순서대로 매긴다.
- **관리자 사양 표시**: 주문 제작·샘플 주문 상세와 견적 상세가 선택지를 모두 그리고 고른 쪽만 채운다
  (`apps/admin/src/shared/ui/custom-option-items.tsx`). `OptionPair`가 N지선다·다중 선택을 받는다.
  "바텍" 표기를 "바택"으로 통일했다(주문 상세, 견적서 엑셀).
- **제작 기간 문구**: 영업일 일수를 주 단위로 바꿨다 — 일반 약 6~8주, 재주문 약 4~6주, 자수·필름 약 3~5주, 원단 직접 제공
  약 2~3주, 샘플 약 6~8주. 주문서의 "주문 전 확인해 주세요" 안내, 정보 탭 네 곳, 샘플 주문 두 곳.

## 결정과 근거 (운영자, 2026-11-18)

- **제작 기간은 주 단위로 넉넉하게**: 예전 숫자(28~42·21~28·7~14)는 전부 7의 배수라 달력 주 단위 값에 "영업일"이 붙은 것으로
  보인다(추정). 영업일 일수는 달력 날짜로 잘못 읽혀 짧아 보이지만, 그렇게 읽은 손님이 그 날짜를 기준으로 기다려 "늦었다"는
  항의가 된다. 단체 넥타이는 행사 날짜에 맞춘 주문이 많고 접수 뒤 취소가 안 되므로 주문 전에 정확히 읽히는 쪽을 택했다.
  영업일 일수와 주를 함께 적는 안, "더 빨리 될 수 있다"는 덧붙임은 넣지 않았다(문구는 단순하게).

- **100개 이상 차단을 없앤 이유**: 차단의 목적은 대량 결제의 토스 수수료 회피였다. 그런데 디자인이 다르면 주문을 나눠야
  해서(디자인마다 제직 기초 비용) 큰 주문일수록 디자인별 100개 미만으로 들어와 차단을 지나간다. 다만 생산 일정 확인과
  세금계산서 수요가 있어 고지는 남겼다. 카드 결제 건에는 세금계산서를 따로 발급하지 않고(부가가치세법 제33조 제2항),
  부가세가 구분된 카드 매출전표로 매입세액공제가 된다(같은 법 제46조 제3항). 토스 매출전표에 부가세가 따로 표시되는 것은
  운영자가 확인했다.
- **견적 연락처를 별도 페이지로**: 주문서에 항상 보이게 두면 구매자 화면에 견적용 칸이 끼어들고, 모달은 배송지 선택 모달과
  겹친다(모달 위 모달 금지).
- **포인트 주문**: 정해진 넥타이 위에 자수·필름만 올린다. 고를 수 있는 건 포인트 방식·타이 방식·라벨·재주문뿐이다.
  원단 직접 제공과의 조합은 택배 수령 절차가 필요해 받지 않는다. 전용 페이지는 만들지 않았다(수량·첨부·요약·버튼·결제가
  전부 겹치고 서버 계산이 하나다).
- **서버는 포인트 주문의 `fabric_provided`를 거절하지 않는다**: 가격에 영향이 없고 예전 스토어가 모든 포인트 주문에
  `true`를 보내 왔다. 스토어는 이제 `false`로 보낸다.
- **견적서 엑셀은 고른 사양만 적는다**: 결재 문서라 안 고른 옵션을 적으면 빠진 항목처럼 읽힌다.

## 플랜과 달라진 것

- 견적 요청 페이지의 연락처 검증은 `invalidCustomOrderSection`의 세 번째 인자 대신 `invalidQuoteContact`로 분리했다.
  주문서 쪽 함수는 사양만 검증한다.
- 히어로 알약은 "견적 요청 가능"을 거치지 않고 바로 "엑셀 견적서 메일"로 바꿨다(절차 5·6을 한 번에 실행).
- 결제 초안의 넥타이 폭은 포인트 주문일 때만 빈 값을 받는다(포인트 주문은 폭 칸이 숨는다 — 안 그러면 결제 페이지가
  초안을 버리고 주문서로 되돌려 보낸다).
- 수선 버튼 문구("장바구니 담기"·"바로주문")는 바꾸지 않았다(선택 항목).

## PR #117 CI·리뷰에서 고친 것

- **DB 제약을 놓쳤다.** `quote_requests`에 `quantity >= 100` 체크 제약이 따로 있어 100개 미만 견적이 409로 떨어졌다(CI의
  `test_quotes.py`가 잡았다). 마이그레이션 `9a4c7e1d5b20`으로 `quantity >= 4`로 바꿨다. 플랜을 쓸 때 서버 코드와 명세만 보고
  DB 모델의 제약을 확인하지 않은 것이 원인이다 — 값의 하한·상한을 바꾸는 플랜은 `db/src/db/models`의 CheckConstraint도 본다.
- 견적 초안에 만든 계정(`ownerUserId`)을 넣고 견적 요청 페이지가 대조한다. 로그인이 끊겼다가 다른 계정으로 돌아오면
  `ProtectedRoute`가 route state를 그대로 복원해 앞 계정의 사양·요청사항이 보일 수 있었다.
- 견적 접수 버튼을 응답 뒤 목록 갱신·이동까지 잠그고, 접수 뒤 이동을 `replace`로 바꿨다(두 번 접수 방지).
- 견적 요청 페이지: 연락처 칸에 API 길이 제한(`maxLength`), 배송지 조회 실패에 "다시 시도".
- 관리자 사양: 문자열이 아닌 옵션 값은 선택지와 맞춰 보지 않고 글자로 보여 준다. 포인트 주문의 딤플·돌려묶기는 고른 것만 보인다.
- 정보 탭: 견적 칸 문구를 "4개부터 요청 가능"으로, 견적서 섹션 버튼의 접근성 이름을 실제 동작(주문서로 이동)으로.
- 반영하지 않은 것: 포인트 주문에 `fabric_provided`·원단 값 표시(포인트 주문은 원단을 쓰지 않는다 — 운영자 결정), 임시 저장
  v3 → v4 이관(운영자가 유실을 감수하기로 했다), 업로드 중 주문서 잠금(구매 흐름과 같은 기존 동작이고 견적 요청 페이지의
  요약에서 확인된다), 포인트 모드에서 숨은 딤플 값 보존(남기면 수동 타이에 딤플이 남아 제출이 막힌다), 만료된 참고 이미지
  재첨부·Enter 제출(기존 주문서·결제 페이지와 같은 수준으로 둔다).

## 확인하지 못한 것

- **DB가 필요한 API 테스트**(`test_orders_create.py`, `test_quotes.py`, `test_estimate_email.py`의 엔드포인트 케이스)는
  로컬 Docker가 꺼져 있어 돌리지 않았다. CI가 돌린다. 특히 새로 넣은 "포인트 + 자동 타이 + 라벨 → 200", "견적 4개 → 201".
- **화면 실측**: 서버를 띄우지 않았다. 주문서 액션 바(375px 폭), 견적 요청 페이지, 정보 탭 견적서 섹션, 관리자 사양 배지의
  줄바꿈은 눈으로 보지 않았다.
- 운영에서의 견적서 메일 도착. 도착하지 않으면 그때 버그로 고치기로 했다.

## 배포 때 감수하는 것

- 배포 순간 주문서를 열어 둔 탭은 임시 저장이 사라진다(`sessionStorage`, 키 v3 → v4).
- 배포 순간 결제창에 있던 손님이 결제에 실패하면 옛 결제 초안(연락처 포함)이 걸러져 주문서로 돌아간다.
- 옛 화면을 열어 둔 탭에서 포인트 주문에 금지 옵션을 보내면 금액 계산이 실패한다. 새로고침하면 풀린다.

## 되돌리는 법 / 상향 신호

- 견적 요청이 소량 건으로 넘쳐 처리가 밀리면 `apps/api/src/api/domains/quotes/service.py`의 하한을 올리고 명세·테스트를
  함께 고친다. 이때 스토어 `requestQuote`에도 같은 하한 검증과 안내 문구를 넣는다(안 그러면 서버의 영문 400 문구가 뜬다).
- 100개 이상 카드 결제가 자주 들어오고 일정 초과 환불이나 세금계산서 재결제 문의가 생기면 100개 이상 구매하기를 막는다.
  비싼 사양 소량 주문에서 같은 문의가 생기면 기준을 수량에서 결제 예상 금액으로 바꾼다.
- 포인트 주문 금액 계산이 `invalid_options`로 실패한다는 문의·로그가 보이면 스토어가 금지 값을 보내고 있다는 뜻이다.
  `calculate_custom_amounts`의 포인트 검증 블록만 되돌리면 서버는 예전처럼 받는다.
- 견적 요청 페이지의 이탈(견적하기 클릭 대비 접수 건수)이 눈에 띄게 높으면 연락처·배송지를 주문서에 두는 안을 재론한다.

## 기각한 대안

- **포인트 + 원단 직접 제공을 서버에서도 거절**: 배포 순서가 조금만 어긋나도 포인트 주문 전체가 막힌다.
- **디자인 여러 개를 한 주문으로 묶는 기능**: 디자인마다 제직 기초 비용이 들어 한 주문으로 작업할 수 없다.
- **관리자 봉제 옵션을 옵션마다 한 행씩**: 사양 카드가 두 배로 길어진다. 배지가 읽기 어렵다는 피드백이 오면 재론.
- **shared의 `decodeOrderItemContent`를 고쳐 고객 화면도 함께 바꾸기**: 고객에게 안 고른 옵션을 보여 달라는 요청이 생기면 재론.
- **제작 기간을 "4~8주"로 넓히기**: 손님은 범위의 앞 숫자를 기억한다. 6~8주로 두기로 했다.
