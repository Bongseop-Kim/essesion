# 실모델 정확도 기준선 — 2026-09-09

사용자의 실행 동의를 받아 유료 provider 호출로 **첫 실모델 기준선**을 만들었다.
같은 날 [엔진 정확도 수정](./design-engine-accuracy-2026-09-09.md)의 후속이며, 그 문서가 남긴
미실행 항목 중 측정으로 닫을 수 있는 것을 함께 닫았다.

이 문서는 두 단계를 담는다: (1) draft 기준으로 만든 첫 기준선, (2) 사람이 기준을 확정한 뒤의 재측정.

고정 조건: 모델 `gpt-5.6-luna`, 임베딩 `text-embedding-3-large`, 저작 프롬프트
`design-plan-v3-example-parameter-reuse-v10-openai-v1`, patch 프롬프트 `design-patch-v5-slot-placement-openai-v1`,
컴파일러 `design-plan-v3.2`, 코드 SHA `3599dd0`, 활성 예시 25건(전부 gallery-v1, 승격분 없음).
코퍼스는 `design-accuracy-v1`(draft)로 시작해 `design-accuracy-v3`(reviewed)로 확정했다 —
**revision이 다르면 수치를 나란히 비교하지 않는다.**

## 무엇으로 측정했나

worker 라우트와 같은 경로(검색 → 저작 → 컴파일 → 제약 → 검증, 편집은 스냅샷 → patch → 적용)를 그대로 타고

subject("원"·"별")만 같은 자리에 공급했다(스크립트 상수, 보고서에 기록).

## 브라우저 실측 (Aside, 2026-09-09)

로컬 store(:3000)·api(:8000)·worker(:8001), 시드 고객 계정, 잔액 5k토큰.

1. 새 세션에서 "네이비 바탕에 작은 꽃과 잎 두 무늬를 격자로 넣어줘" → 모티프 2/2, 격자 배치 생성.
2. "꽃과 잎을 모두 흩뿌려 주세요" → 두 레이어 모두 `type=scatter, min_dist_mm=12, count=8`으로 바뀌고
   `seed_salt`가 각각 `motif_0`·`motif_1`로 붙었다(DB `design_sessions.current_intent` 확인).
3. 같은 intent에서 salt만 제거해 재계산한 결과는 **두 레이어의 8개 좌표가 완전히 동일**했다 —
   수정 전이라면 잎이 꽃 아래 정확히 가려졌다는 뜻이다. 수정 후에는 좌표가 서로 다르고,
   화면·이력 썸네일에서도 꽃과 잎이 각각 보인다.
4. 콘솔 오류 없음. 넥타이/타일 뷰 모두 정상 렌더.

## 기준 확정과 재측정 (같은 날, 사람 확정 후)

아래 3건을 사람이 확정해 문장·조건을 고쳤다(`design-accuracy-v3`, `review_status=reviewed`).
채점기에는 첫 생성의 정도 표현을 판정할 `lte`/`gte` 연산을 더했다 — 첫 생성에는 비교할 baseline이 없다.

| revision | 무엇이 달라졌나 | 결과 |

| v2 | 002 "아주 작게"+`lte 0.12`, 006 방향 명시, 024 축당 개수 | 29/30. 006·024 통과. 002는 **바탕색**(#103A40)이 틀렸다 |

v2 → v3 재조정의 근거: 0.12는 내가 임의로 잡은 값이었고, 이 엔진이 "작은 모티프"라고 부르는 크기는

배제한다. 느슨하게 만든 것이 아니라 엔진의 기준에 맞춘 것이다 — v1이 낸 0.167은 v3에서도 실패한다.

**주의해서 읽을 것**

- 30/30은 "모델이 완벽하다"가 아니라 **이 30건이 현재 모델을 더 이상 변별하지 못한다**는 뜻이다.
  변별력을 되찾으려면 사례를 늘려야 한다(남은 플랜 2번).
- v2에서 한 번 나온 바탕색 오류(흰색 요청 → 짙은 청록)는 v3 문장으로 2회 모두 재현되지 않았다.
  문장이 달랐으므로 원인을 단정할 수 없다. **지명색 오류가 사라졌다고 결론 내리지 않는다** — 표본이 작다.
- 조건은 다 통과해도 **출력은 매번 같지 않다**: v3 두 실행에서 최종 intent가 완전히 같은 사례는 23/30이고,
  나머지 7건은 크기·밴드 폭 같은 조건이 걸지 않은 축에서 달랐다. 코퍼스가 고정하는 것은 의미이지 바이트가 아니다.
- 지연은 평균 3.1초, p95 3.5~4.6초, 저작 시도 1.03~1.07회로 v1과 같은 수준이다.

## 변별력 보강과 그때 드러난 결함 (v4·v5)

v3에서 30/30이 나와 코퍼스가 모델을 변별하지 못했다. 사용자가 문장 목록을 보고 판단을 위임해
7건을 더했다(`design-accuracy-v4` → 조건 수정 후 `v5`).

| 사례 | 무엇을 노렸나 |
|---|---|
| 031·032 | 색과 역할의 결합을 문장 순서로 뒤집고, 이름 옆에 **명시 hex**를 붙였다 |
| 033 | 한 줄무늬 안에 굵은 흰 줄 + 가는 금 줄을 쌍으로 — 색 순서까지 본다 |
| 034·035 | 추상 요청("차분한 봄 느낌", "화려한 파티용")이 명시 조건을 흔드는지 |
| 036·037 | 한 문장이 두 대상을 반대로 움직이기, 한 슬롯만 줄 위로 |

| 실행 | 코드 | 결과 |

세 실행 모두 `v5` 기준으로 다시 채점한 수치다.

### 찾은 결함: 명시 hex를 지명색 표가 덮어썼다

`금색 #FFD700`을 달라고 했는데 `#D4AF37`이 나왔다. 모델이 아니라
[named_colors.py](../../apps/worker/src/worker/adapters/named_colors.py)의 결정론적 접지가 원인이었다 —
"금색"이라는 단어를 보고 표의 hex로 슬롯을 덮어썼고, 사용자가 바로 옆에 적은 값을 무시했다.
두 실행에서 두 사례 모두 재현됐다(모델 변동이 아니다).

고침: **이름 옆에 hex가 붙어 있으면 그 hex가 이긴다.** 이름만 있으면 종전대로 표 값으로 접지한다.
회귀 테스트를 붙였고(`test_adapters.py`), 고친 뒤 031·033을 다시 돌려 `#FFD700`이 그대로 나오는 것을 확인했다.
명세는 `worker-pipeline.md` §5에 기록했다.

### 함께 고친 판정 기준 (v4 → v5)

`stripe.colors`는 색뿐 아니라 **밴드 개수와 순서**까지 고정한다. "줄무늬는 흰색"처럼 색만 지정한 문장에
흰 줄 두 개가 나오면 요청은 맞는데 조건이 틀렸다고 잡혔다(v4c의 032). 색만 지정한 첫 생성 사례
(004·005·006·031·032)는 쓰인 색 집합을 보는 `stripe.colors_used`로 바꾸고, 구조까지 지정한 033은
순서 있는 `stripe.colors`를 유지했다. **조건을 느슨하게 만든 것이 아니라 문장이 정하지 않은 축을 뺐다.**

### 그 밖에 관측한 것

- **036은 불안정하다**: "원은 크게, 별은 작게"가 4회 중 1회 아무 축도 채우지 않은 빈 patch(`no_change`)로
  끝났다. 나머지 3회는 정상(원 5.0 / 별 3.0). 재현되는 실패가 아니라 **간헐적 무응답**이다.
- **RAG A/B에 처음으로 차이가 보였다**: 첫 생성 13건에서 예시 있음 **13/13**, 예시 없음 **12/13**.
  갈린 사례는 002("작게")로, 예시가 있으면 갤러리의 "작은 모티프" 값 0.125를, 없으면 0.14를 냈다.
  1건 차이이므로 **RAG가 효과 있다고 단정하지 않는다** — 방향과 메커니즘만 관측됐다.
  (같은 실행에서 provider 오류 1건이 나 그 사례는 따로 다시 수집했다.)
- 지연은 평균 2.8초, p95 3.7초, 저작 시도 1.05회로 v1~v3과 같은 수준이다.
